# 风险与改进建议

## 1. 总体判断

当前项目已经具备较清晰的研究目标和一定的工程骨架，但仍处于“验证逻辑与产品逻辑尚未完全收敛”的阶段。主要风险不是算法方向错误，而是：

- 输入语义不统一
- 主程序与 notebook 脱节
- 路径和参数存在硬编码
- 部分实现仍带有原型性质

这些问题如果不先梳理，会直接影响阵型接口、四指标迁移和报告生成功能的稳定落地。

## 2. 高优先级风险

### 2.1 输入字段语义与单位不一致

#### 问题

当前代码、测试样例和 notebook 对多个关键字段的定义并不一致：

- `Central_F` 在部分代码注释中被写成 MHz，在 JSONC 中实际按 GHz 使用。
- `Bandwidth` 的命名和返回接口中同时出现 MHz、KHz 表述。
- `Sensitivity` 在 JSONC 中有正值写法，而 notebook 会在解析时手动取负，`DataModel` 校验却假定它本身就是负 dBm。
- `interferenceMargin` 在设计文档中既被当作干扰阈值使用，也被当作等效带外抑制度使用。

#### 影响

- 主程序结果、UI 输入和 notebook 结果无法保证严格同口径。
- 后续把四项指标迁回 C++ 时容易出现“代码能跑，但意义不一致”的问题。

#### 建议

1. 先给出统一 schema 文档。
2. 统一频率、带宽、灵敏度、干扰阈值的单位和符号约定。
3. 在解析层就完成标准化，不把符号修正散落在 UI、解析器和 notebook 中。

### 2.2 设备 ID 设计存在结构性歧义

#### 问题

当前 `Tests/Test*.jsonc` 中大量设备使用相同的 `ID`，例如多艘船都使用 `Device1`、`Device2`。而 `TransferToEngine` 在转换时通过 `equipmentID` 构建哈希表，默认把它当作全局唯一键。

#### 影响

- 不同船只上的同名设备可能相互覆盖。
- 当设备参数不再完全一致时，会导致错误设备被绑定到错误船只。
- 这会直接破坏后续阵型扩展、多设备建模和链路级评估。

#### 建议

1. 设备唯一标识改为全局唯一，例如 `USV1_TX1`、`USV3_RX1`。
2. 或在数据结构上改为“设备为船只的内嵌对象”，不再单独依赖全局平铺索引。
3. `EquipmentOnShip` 至少应使用“船只 ID + 设备 ID”的组合键。

### 2.3 主程序输入路径硬编码且与现有样例不一致

#### 问题

`Simulation.cpp` 中当前硬编码加载：

- `D:/code/Electromagnetic_compatibility/tests/Test.json`

而仓库中实际主要样例是：

- `Tests/Test.jsonc`
- `Tests/Test_A.jsonc`
- `Tests/Test_B.jsonc`

#### 影响

- 工程在不同机器上无法直接运行。
- 主程序实际读取的文件与验证资产不一致。
- 后续阵型模板、报告生成等功能很难建立在稳定输入源之上。

#### 建议

1. 改为仓库相对路径。
2. 正式支持 `jsonc` 扩展名。
3. 在 UI 中提供“选择配置文件 / 选择内置场景”的入口。

### 2.4 主程序与 notebook 指标链路脱节

#### 问题

实验三已经在 notebook 中定义并计算了：

- `SCF`
- `S3I`
- `T_elev`
- `D_desense`

但主项目当前真正落地的仍主要是二维 PE 场分布聚合。

#### 影响

- 用户看到的桌面端结果与论文侧结论并不等价。
- 报告生成功能没有稳定的结构化指标输入。
- 后续讨论“EMC 评价”时容易把验证逻辑误认为主程序已实现能力。

#### 建议

1. 把四指标的输入、输出和中间数据结构先从 notebook 梳理出来。
2. 明确哪些部分可直接迁移，哪些部分需重新设计为 C++ API。
3. 以“先实现结构化指标结果，再做报告生成”为原则推进。

### 2.5 校验规则与设计文档冲突

#### 问题

当前若从 UI 角度使用 `DataModel` 校验规则，会与 `DESIGN.md` 和 A/B 场景存在冲突：

- 发射机角度校验限制为 `[0, 180]`，但 `Case B` 中存在 `210°`、`240°`、`270°` 等角度。
- 接收机 `interferenceMargin` 校验要求小于 `0`，而高危 `Case A` 中存在 `0` 的设定。
- 接收机灵敏度校验规则也与样例值存在偏差。

#### 影响

- 设计文档中的场景在 UI 中可能根本无法通过校验。
- “文档合法、程序非法”的状态会持续积累。

#### 建议

1. 先统一配置语义，再重新设计校验规则。
2. 校验规则应服务于工程真实场景，而不是把当前样例拒之门外。
3. 把“物理合理性校验”和“推荐值提示”分开。

## 3. 中优先级风险

### 3.1 EnvironmentData 尚未形成稳定配置入口

#### 问题

当前 `JsonLoader` 主要解析船只和设备，对 `EnvironmentData` 的配置支持较弱，很多环境参数仍依赖默认值或在代码中直接修改。

#### 影响

- 实验可复现性较差。
- 同一输入文件无法完整表达仿真任务。

#### 建议

把环境参数纳入统一配置 schema，包括：

- `max_range`
- `duct_height`
- `wind_speed`
- `dx`
- `dz`
- `nz`
- `angle_step_deg`

### 3.2 接收机高度与部分传播参数存在硬编码

#### 问题

当前主流程中存在固定值：

- `receiver_height = 25.0`
- 若干验证函数里直接覆写 `_env`

#### 影响

- 仿真结果强依赖代码默认值。
- 设备级差异无法准确体现在结果中。

#### 建议

1. 从接收机对象或配置中读取接收高度。
2. 把验证场景参数和业务场景参数明确分开。

### 3.3 二维地图坐标系与范围假设较强

#### 问题

`PEmodel_computing2D()` 当前使用：

- `map_width_m = env.max_range`
- `map_height_m = env.max_range`
- 输出原点位于左上角

这意味着地图边界与发射机位置、编队整体范围之间的关系并不严格受控。

#### 影响

- 当发射机靠近边界或编队跨度增大时，结果可能被裁剪。
- A/B 阵型扩大后，更容易暴露坐标范围不足问题。

#### 建议

1. 将地图范围定义为“场景边界”而不是“最大传播距离”。
2. 支持以编队包围盒自动扩展结果网格。
3. 明确世界坐标系与图像坐标系的映射约定。

### 3.4 线程模型仍偏原型化

#### 问题

当前通过 `std::thread` 驱动 `EMC_Engine` 执行仿真，再以 Qt 信号回调 UI。对于 `QObject` 生命周期、线程亲和性和停止语义，设计还不够稳健。

#### 影响

- 后续一旦增加更长时任务、取消任务、批量任务或报告生成流程，线程管理复杂度会迅速升高。

#### 建议

1. 中长期可考虑迁移为 `QThread` 或统一任务执行器。
2. 明确“仿真任务对象”“结果对象”“取消信号”的边界。

### 3.5 结果导出接口较分散

#### 问题

当前结果输出包括：

- UI 图表
- `CSV`
- notebook 图表
- Markdown / HTML 报告

但缺乏统一结果模型。

#### 影响

- 每新增一种展示方式，都需要重新拼装数据。
- 报告生成难以复用已有结果。

#### 建议

先定义一个统一的“仿真结果对象”，再由它派生：

- UI 展示结果
- 指标结果
- 报告输入
- 导出文件

## 4. 低优先级问题与代码清理点

### 4.1 验证函数中存在未完成或不一致实现

例如：

- `do_PE_test()` 中 `return` 之后还有 `emit`，属于不可达代码。
- 部分验证函数中初始化与步进调用被注释掉，说明仍处于实验性状态。

建议把“验证草稿代码”和“正式主流程代码”分开管理，避免后续维护时误用。

### 4.2 命名与拼写不统一

当前存在多处命名问题，例如：

- `Reciever` / `Receiver` 混用
- `Bandwith` 拼写问题
- `getBandwidthKHz()` 实际处理的是 MHz 语义

这类问题单独看不致命，但会在接口收敛阶段显著增加理解成本。

### 4.3 源码注释与编码风格需要统一

项目希望新增文档和说明都使用中文，但当前源码注释、命名风格、注释编码并不完全统一。建议后续新改动统一采用 UTF-8 和中文说明口径，逐步消化历史遗留风格差异。

## 5. 建议的改进顺序

结合 `TODO.md`，建议按以下顺序推进：

### 第一步：先统一配置与语义

- 统一 JSONC schema
- 统一字段单位与正负号语义
- 修正设备唯一标识方案
- 移除硬编码路径

### 第二步：再把实验三指标迁回主项目

- 提炼 `SCF`
- 提炼 `S3I`
- 提炼 `T_elev`
- 提炼 `D_desense`

目标是让主程序具备与 notebook 一致的结构化 EMC 指标结果。

### 第三步：在指标稳定后扩展阵型与报告

- 增加内置阵型模板
- 支持输入配置按阵型重排
- 基于统一结果对象生成评估报告

### 第四步：最后再系统优化前端展示

- 丰富二维图、矩阵图、曲线图、热图展示
- 加入 A/B 场景对照视图
- 提升用户对“传播结果”和“EMC 评价结果”的区分感知

## 6. 结论

当前项目最需要的不是继续堆功能，而是先完成三件基础工作：

1. 统一输入语义与配置 schema。
2. 打通主项目与 `experiment3.ipynb` 的指标链路。
3. 把结果组织成稳定的结构化 API，而不是只停留在图和 CSV。

只要这三件事完成，后续的阵型模板、报告生成和前端展示都会自然顺下来；否则每增加一个功能，都会反复撞到相同的接口和语义问题上。
