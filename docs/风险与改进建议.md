# 风险与改进建议

## 1. 现状判断

当前项目已经从“多套输入口径并存”收敛到“主程序只认一套新 schema”，这是明显进展；但整体仍处于“接口已初步统一、主程序与验证侧尚未完全打通”的阶段。

现在的主要风险已经不再是“有没有 schema”，而是“schema、内部 DTO、UI 校验、验证侧口径能否长期保持一致”。

## 2. 已完成的收敛项

### 当前已实现

- 已建立新的标准输入 schema，并形成 `README + schema.json + template.jsonc` 三件套文档。
- 主程序 `JsonLoader` 已切换为只支持新 schema，不再兼容旧格式。
- `JsonLoader` 已使用 `Interface/SchemaConstants.h` 约束字段名、固定值和枚举值。
- `EnvironmentData` 的主要参数已进入 `Tests/Test.jsonc`，不再只依赖 `DataModel.h` 默认值。
- `PE_validation` 已拆为独立 Git 子模块，主程序与验证侧资产的边界更加清晰。

### 验证侧已有

- `PE_validation` 中已沉淀实验 1 到实验 3 的 notebook、图表与结论。
- A/B 场景、EMC 指标口径和验证流程已有较完整的实验侧资产。

### 仍需后续实现

- 主程序仍未正式输出实验 3 所需的结构化 EMC 指标。
- 配置入口仍未从“测试样例驱动”升级为“用户可选场景驱动”。

## 3. 高优先级风险

### 3.1 `Simulation.cpp` 仍依赖绝对路径

#### 问题

当前 `Simulation::on_StartSimulate_clicked()` 仍直接加载：

- `D:/code/Electromagnetic_compatibility/Tests/Test.jsonc`

这说明主程序虽然已经切到新 schema，但配置入口仍然是开发机路径。

#### 影响

- 工程在其他机器上不能直接复用该入口。
- 难以支持多场景切换、阵型模板和用户自选配置。
- 文档只能把它记为“现存风险”，不能描述成“已完成标准化接入”。

#### 建议

1. 先改为仓库相对路径。
2. 再补一个 UI 选择配置文件或选择内置样例的入口。
3. 后续把“当前场景”抽象成明确的仿真任务对象。

### 3.2 新 schema 与旧 DTO 命名仍并存

#### 问题

外部输入已经统一为：

- `centerFrequencyGHz`
- `bandwidthMHz`
- `shipOrientationDeg`
- `sensitivityDbm`

但内部 `DataModel` 仍保留大量旧字段名，例如：

- `CentralF_Reciever`
- `Bandwidth_Reciever`
- `ship_Orienteation`
- `Sensitive_reciever`

同时，部分代码注释仍保留旧单位或旧语义。

#### 影响

- 后续维护者很容易误判单位和物理含义。
- 文档、UI、解析器、算法层之间容易再次出现语义漂移。
- 新增 EMC 指标或报告接口时，转换层复杂度会持续升高。

#### 建议

1. 先统一注释与文档口径。
2. 再视改动范围，逐步把 DTO 成员名向新 schema 靠拢。
3. 若短期不改成员名，至少补清晰的映射说明，避免隐式语义转换。

### 3.3 UI 校验规则与新 schema 语义可能冲突

#### 问题

`JsonLoader` 当前按新 schema 解析，但 `DataModel.h` 中仍存在历史校验逻辑，例如：

- `Sensitivity` 标准已固定为负值，但 `validate_reciever()` 进一步要求其不得高于 `-90 dBm`
- `interferenceMargin` 在 schema 中允许一般数值，但旧校验逻辑要求其必须小于 `0`
- `gainDbi` 从物理上允许出现负值，但旧基础校验仍默认增益不能为负

#### 影响

- 可能出现“schema 合法，但 UI 校验不通过”的双重标准。
- 主程序手动录入与文件导入的行为边界不清晰。
- 后续如果引入更多设备类型，旧校验逻辑会持续阻碍扩展。

#### 建议

1. 以新 schema 为主，重新梳理 UI 校验规则。
2. 把“硬约束校验”和“推荐值提示”分开。
3. 对 `gainDbi`、`sensitivityDbm`、`interferenceMarginDb` 等字段补统一口径说明。

### 3.4 历史样例仍可能误导使用者

#### 问题

仓库中仍保留：

- `Tests/Test_A.jsonc`
- `Tests/Test_B.jsonc`

它们属于历史样例，不再是主程序标准输入，但如果文档标注不清，会被误认为与 `Tests/Test.jsonc` 等价。

#### 影响

- 新使用者可能继续按旧字段组织数据。
- 分析问题时会把历史样例误当作主链路接口。
- 后续维护时容易重复引入旧字段兼容讨论。

#### 建议

1. 在文档中明确其为历史参考样例。
2. 如后续不再需要，可转移到单独的 `legacy` 或说明目录。
3. 主程序入口、截图和文档示例统一使用 `Tests/Test.jsonc`。

### 3.5 主程序与验证侧指标链路仍未打通

#### 问题

`PE_validation` 已有实验 3 的指标定义和图表结论，但主程序当前真正稳定输出的仍主要是二维场结果。

#### 影响

- “验证侧已有”与“主程序已实现”容易被误混。
- 报告生成功能缺少结构化指标输入。
- 未来要把 notebook 能力迁回 C++ 时，仍要再次梳理数据边界。

#### 建议

1. 先定义主程序侧 EMC 指标结果对象。
2. 再按对象边界迁移 `SCF`、`S3I`、`T_elev`、`D_desense`。
3. 最后再实现报告生成与 A/B 自动对比。

## 4. 中优先级风险

### 4.1 `EnvironmentData` 的代码实现与文档仍有细节不一致

例如：

- `ship_Speed` 注释中仍残留 `knots / m/s` 混用痕迹
- `EnvironmentData` 的历史注释仍有旧步进说明
- `validate_EnvironmentConfig()` 的返回逻辑本身也不完整

这些问题不会立刻阻塞编译，但会削弱接口可信度。

### 4.2 结果对象仍偏“绘图导向”

当前主程序以 `GridMap` 和图表显示为核心，缺少稳定的结构化结果对象来承接：

- 指标计算
- 报告生成
- 场景对比
- 导出接口

如果不先建立统一结果模型，后续每新增一类输出都会重新拼装数据。

### 4.3 线程与任务边界仍偏原型化

当前仿真入口通过 `std::thread` 驱动 `EMC_Engine`，能工作，但对以下场景的支持仍偏弱：

- 取消任务
- 批量任务
- 多场景排队
- 报告生成串联

这不是当前最紧急的问题，但在功能扩展后会变成瓶颈。

## 5. 建议的推进顺序

1. 先消除绝对路径入口，建立稳定的配置加载方式。
2. 统一 `DataModel` 注释、字段映射说明和 UI 校验口径。
3. 定义主程序侧结构化 EMC 指标结果对象。
4. 把验证侧实验 3 指标迁回主程序。
5. 在结果对象稳定后，再接阵型模板、A/B 对比和报告生成。

## 6. 结论

当前最关键的不是继续堆叠界面能力，而是保持以下三者长期同口径：

1. 新 schema 文档
2. 主程序运行时代码
3. `PE_validation` 中的验证结论

这一步已经完成了第一阶段收敛，但还没有走到“接口彻底稳定”。接下来应优先解决配置入口、旧 DTO 口径残留和 EMC 指标迁移这三类问题。
