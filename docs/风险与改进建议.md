# 风险与改进建议
**注意: 不需要修改验证测代码,不需要处理验证测与主项目的兼容性,验证侧仅用于上下文参考**
## 1. 现状判断

当前项目已经从“多套输入口径并存”收敛到“主程序只认一套新 schema”，并且 UI 主链路闭环、仿真任务控制、JSON 导入与只读树状总览都已落地。按本轮用户回传结果，自动测试与手动验证也已完成。

因此当前最主要的风险，已经从“基础链路是否能跑通”转向“口径能否长期保持一致”和“后续产品化能力如何继续扩展”。

## 2. 已完成的收敛项

### 当前已实现

- 已建立新的标准输入 schema，并形成 `README + schema.json + template.jsonc` 三件套文档。
- 主程序 `JsonLoader` 已切换为只支持新 schema，不再兼容旧格式。
- `JsonLoader` 已使用 `Interface/SchemaConstants.h` 约束字段名、固定值和枚举值。
- `EnvironmentWidget` 已补齐，环境、设备、船只三类编辑页均统一收敛到 `DataModel::validateSnapshot()`。
- 主窗口已提供 `JSON/JSONC` 导入入口，并在导入成功后统一回填页面草稿。
- 仿真入口已不再强制重载绝对路径 `Tests/Test.jsonc`，而是统一消费当前 `DataModel` 快照。
- `Home/TreeView` 已提供 `DataModel` 的只读树状总览，支持刷新、展开、折叠和关键字查找。
- `LogWidget`、`Home`、`DeviceonShip` 的关键稳定性问题已按本轮规格修复。
- `PE_validation` 已拆为独立 Git 子模块，主程序与验证侧资产的边界更加清晰。

### 验证侧已有

- `PE_validation` 中已沉淀实验 1 到实验 3 的 notebook、图表与结论。
- A/B 场景、EMC 指标口径和验证流程已有较完整的实验侧资产。

### 仍需后续实现

- 主程序虽已正式输出 `DerivedMetrics`，但报告生成、结果持久化和历史任务消费链路仍未落地。
- 任务历史、最近导入记录、场景模板等产品化能力尚未形成稳定方案。

## 3. 高优先级风险

### 3.1 JSON 导入会直接覆盖未保存草稿

#### 现状

当前主程序已在检测到页面存在未保存草稿时，使用 `ElaContentDialog` 做导入前确认；只有用户明确确认后，才会继续选择并导入 `JSON/JSONC` 文件。

#### 剩余风险

- 当前已拦截“误点导入后直接覆盖草稿”的高风险路径，但仍未提供导入前差异预览。
- 若用户确认覆盖后才意识到选错文件，当前仍没有“恢复最近一次草稿”的能力。

#### 建议

1. 如需进一步降低误操作成本，可增加“导入前预览/差异提示”能力。
2. 如后续进入更强产品化阶段，可补充最近一次草稿恢复能力。

### 3.2 新 schema 与旧内部命名并存问题已基本收敛

#### 现状

外部输入已经统一为：

- `centerFrequencyGHz`
- `bandwidthMHz`
- `shipOrientationDeg`
- `sensitivityDbm`

当前 `DataModel` 中与主输入链路直接相关的 DTO 字段已改为新 schema 命名，例如：

- `receiverCenterFrequencyGHz`
- `receiverBandwidthMHz`
- `shipOrientationDeg`
- `receiverSensitivityDbm`

#### 剩余风险

- 仍有部分 UI 控件成员名、局部变量名保留历史拼写，这些名称不再属于对外接口，但会增加局部维护成本。
- 如果后续继续扩展环境配置 UI、任务管理或结果对象，仍需要持续避免把历史命名重新带回 DTO 或文档层。

#### 建议

1. 保持 `SchemaConstants.h -> DTO -> 文档` 三处同口径。
2. 后续仅在局部重构时清理 UI 内部历史变量名，不再把它们视为接口级风险。

### 3.3 UI 校验分层已建立，但后续新增页面仍有回归风险

#### 现状

当前分层已经收敛为：

- `JsonLoader` 只负责字段存在性、类型、固定值、枚举值和未知字段拦截等基础校验
- UI 页面只负责中文界面输入、DTO 组装和基础格式校验
- `DataModel::validateSnapshot()` 统一负责核心语义校验

#### 剩余风险

- 这套分层现在已经覆盖环境页、设备页、船只页与 JSON 导入路径，但未来新增页面或新输入字段时，仍可能把语义规则重新散落回 UI 层。
- `TreeView` 当前依赖 `DataModel` 作为唯一真相源；若后续出现绕过 `DataModel` 的局部状态扩展，首页展示与编辑页状态可能再次失同步。

#### 建议

1. 新增输入字段时先更新 `SchemaConstants.h` 与 `DataModel`，再扩展 UI。
2. 对新的页面能力继续沿用 `loadFromModel()/saveToModel()/setReadOnly()/dirty` 契约，避免出现例外路径。

### 3.4 历史样例仍可能误导使用者

#### 问题

仓库中仍保留：

- `Tests/Test_A.jsonc`
- `Tests/Test_B.jsonc`

它们属于历史样例，不再是主程序标准输入，但如果文档标注不清，会被误认为与 `Tests/Test.jsonc` 等价。

#### 影响

- 新使用者可能继续按旧字段组织数据。
- 分析问题时会把历史样例误当作主链路接口。
- 后续维护时容易重复引入旧字段兼容讨论。

#### 建议

1. 在文档中明确其为历史参考样例。
2. 如后续不再需要，可转移到单独的 `legacy` 或说明目录。
3. 主程序入口、截图和文档示例统一使用 `Tests/Test.jsonc`。

### 3.5 主程序与验证侧指标链路已打通，但仍需持续校准口径

#### 现状

`PE_validation` 中的实验 3 指标定义、图表和评估逻辑已经迁回主程序结果对象，当前 `SimulationTaskResult::derivedMetrics` 已正式承载：

- `SCF`
- `S3I`
- `T_elev`
- `D_desense`

同时，主程序已新增：

- `emcAnalysisConfig`
- `EMCMetricsCalculator`
- 结果侧 schema / template

#### 剩余风险

- 验证侧已有的 notebook 结论仍然是重要参照物，主程序后续迭代时仍需防止公式口径和图表口径再次漂移。
- 当前 `victimReceiverId` 第一版固定等于 `referenceReceiverId`，尚未扩展到多受害机建模。
- 主程序已经能输出结构化指标，但报告模块和 A/B 自动对比还未真正消费这些字段。

#### 建议

1. 后续若调整指标公式或字段结构，先同步更新结果 schema 与测试，再改运行时代码。
2. 让报告生成与场景对比统一消费 `SimulationTaskResult`，不要再回退到按图表二次拼装数据。
3. 在多受害机或更多评估口径进入主程序前，先稳定当前四指标的字段边界。

## 4. 中优先级风险

### 4.1 `EnvironmentData` 默认值仍可能掩盖空模型与真实输入差异

当前环境页已经补齐，JSON 输入与 UI 录入对 `EnvironmentData` 的覆盖链路也已基本对称。

剩余问题是：

- `EnvironmentData` 仍保留一组回退默认值，用于空模型或 UI 初始态。
- 如果后续没有在页面文案、日志或任务状态中明确区分“默认值”与“用户真实输入”，排查问题时会增加理解成本。

这不会直接破坏 schema/DTO 一致性，但会影响问题定位效率。

### 4.2 结果对象已结构化，但消费链路仍偏“展示优先”

当前主程序已经引入稳定的 `SimulationTaskResult` 结果边界，并正式承载 `DerivedMetrics`。剩余问题不再是“没有结果对象”，而是这些结构化结果目前仍主要被 UI 展示层直接消费，以下能力尚未接上：

- 指标计算
- 报告生成
- 场景对比
- 导出接口

如果后续不继续围绕 `SimulationTaskResult` 收敛消费链路，仍然会重新出现“各模块各自拼数据”的风险。

### 4.3 线程与任务边界仍偏原型化

当前仿真页已经具备显式任务状态、只读切换和取消入口，但底层仍主要通过 `std::thread` 驱动 `EMC_Engine`，对以下场景的支持依然偏弱：

- 更细粒度的取消中断点
- 批量任务
- 多场景排队
- 报告生成串联

这不是当前最紧急的问题，但在功能扩展后会成为瓶颈。

### 4.4 `TreeView` 当前只读，不承担首页导航职责

当前首页树视图已经能稳定展示 `DataModel`，但它的范围是明确收敛的：

- 不支持编辑
- 不支持勾选或删除
- 不支持节点跳转到具体编辑页

这不是实现缺陷，而是当前阶段的有意边界。若后续要把首页做成真正的工作台，需要重新设计树节点交互与状态联动，而不是直接在只读实现上叠加行为。

## 5. 建议的推进顺序

1. 先补齐导入覆盖草稿时的交互策略与恢复策略。
2. 让报告生成、场景对比和结果导出统一消费 `SimulationTaskResult`。
3. 深化 `DerivedMetrics` 的后续消费能力，而不是重新发散回图表级临时结构。
4. 深化任务体系，补齐更稳健的取消、排队和任务历史。
5. 在主链路稳定后，再评估首页导航化、任务模板与报告导出的产品化设计。

## 6. 结论

当前最关键的不是继续堆叠页面数量，而是保持以下三者长期同口径：

1. 新 schema 文档
2. 主程序运行时代码
3. `PE_validation` 中的验证结论

这一步已经完成了 UI 主链路第一阶段闭环，后续工作的重点应从“补最基本入口”转到“把结果对象、任务体系和产品化交互做扎实”。

## 7. 2026-04-29 仿真结果边界进展
### 当前已实现
- 4.2 中提到的“结果对象仍偏绘图导向”已开始收敛：主程序已引入 `SimulationTaskResult` 作为结果根对象。
- `EMC_Engine` 不再直接作为 UI 的最终结果边界，而是输出 `EMCComputationResult`。
- 单发射机求解职责已拆到 `PEPropagationSolver`，任务组装职责已上移到 `simSchedulerCtx`。
- 仿真页已经改为消费 `SimulationTaskResult`，并通过 `inputSnapshot` 保持“当前结果对应旧输入”的提示能力。
- 文档层已新增结果 schema 和模板，结果对象字段口径得到固定。
- `DerivedMetrics` 已正式承载 `SCF / S3I / T_elev / D_desense`，并由独立的 `EMCMetricsCalculator` 统一计算。

### 验证侧已有
- `PE_validation` 中关于实验 3 指标的定义、图表和评估逻辑仍然存在，后续主程序校准和回归仍需参考这些资产。

### 剩余风险
- `formationSource + presetFormationId` 只是字段预留，预设编队如何改造输入后再仿真，还没有形成稳定业务方案。
- 结果对象已适合作为报告和多样化展示的统一输入，但结果持久化、任务历史和报告模块仍缺失。
- `DerivedMetrics` 已进入主程序，但多受害机扩展、更丰富评估口径与统一导出仍是后续工作。

### 建议后续实现
1. 让报告生成与场景对比统一消费 `SimulationTaskResult`，避免再次回到“按图拼数据”。
2. 单独设计预设编队链路，把 `presetFormationId` 从保留字段升级为真实输入能力。
3. 在保持当前四指标稳定的前提下，再评估多受害机和更多派生指标扩展。

## 8. 2026-04-30 仿真页结果画廊风险更新
### 当前已实现
- 仿真页结果展示已开始从“单图绘制”切到“六张固定结果卡片 + 单详情区”结构。
- 结果目录抽取与绘图职责已拆分为独立层，避免继续把展示逻辑堆回 `Simulation.cpp`。
- 参考发射机筛选口径已固定为 `inputSnapshot.emcAnalysisConfig.referenceTransmitterId`。
- `SCF / S3I / T_elev / D_desense` 已按图类型进入统一展示入口，不再要求 UI 侧二次计算。

### 剩余风险
- 本轮未运行 `cmake` 构建与测试，当前收口结论仍以静态代码检查为主，尚缺一次真实编译验证。
- 结果画廊当前只覆盖六类主图，尚未扩展到更多诊断切片、多参考链路或多受害机浏览。
- `ElaScrollPageArea` 本身不是通用图表容器，页面高度与卡片换行逻辑后续仍需结合真实窗口尺寸继续打磨。

### 建议
1. 由用户在本地执行一次最小构建，优先确认 `Simulation.cpp`、`SimulationResultCatalog.cpp` 和 `SimulationResultGalleryTests.cpp` 的编译接线。
2. 编译通过后，再做一轮手动页面联调，重点检查六张卡片顺序、默认选中、参考发射机筛选和详情区切换。
3. 在结果页交互稳定前，不要再把额外展示需求直接塞进 `Simulation.cpp`，应继续复用目录抽取层和统一绘图器。
