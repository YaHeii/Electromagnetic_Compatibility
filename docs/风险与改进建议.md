# 风险与改进建议

## 1. 现状判断

当前项目已经从“多套输入口径并存”收敛到“主程序只认一套新 schema”，这是明显进展；但整体仍处于“接口已初步统一、主程序与验证侧尚未完全打通”的阶段。

现在的主要风险已经不再是“有没有 schema”，而是“schema、内部 DTO、UI 校验、验证侧口径能否长期保持一致”。

## 2. 已完成的收敛项

### 当前已实现

- 已建立新的标准输入 schema，并形成 `README + schema.json + template.jsonc` 三件套文档。
- 主程序 `JsonLoader` 已切换为只支持新 schema，不再兼容旧格式。
- `JsonLoader` 已使用 `Interface/SchemaConstants.h` 约束字段名、固定值和枚举值。
- `EnvironmentData` 的主要参数已进入 `Tests/Test.jsonc`，不再只依赖 `DataModel.h` 默认值。
- `DataModel` 的核心 DTO 字段已与新 schema 命名对齐，`TRANSCEIVER` 已收编为正式 schema 枚举。
- 船只/设备 UI 已改为“中文界面 + DTO 组装 + 基础校验”，核心语义校验统一收口到 `DataModel::validateSnapshot()`。
- 仿真入口已不再强制重载绝对路径 `Tests/Test.jsonc`，而是统一消费当前 `DataModel` 快照。
- `PE_validation` 已拆为独立 Git 子模块，主程序与验证侧资产的边界更加清晰。

### 验证侧已有

- `PE_validation` 中已沉淀实验 1 到实验 3 的 notebook、图表与结论。
- A/B 场景、EMC 指标口径和验证流程已有较完整的实验侧资产。

### 仍需后续实现

- 主程序仍未正式输出实验 3 所需的结构化 EMC 指标。
- 配置入口仍未从“测试样例驱动”升级为“用户可选场景驱动”。

## 3. 高优先级风险

### 3.1 外部 JSON 入口仍未显式产品化

#### 现状

`Simulation.cpp` 已不再依赖开发机上的绝对路径测试文件，运行入口统一改为消费当前 `DataModel` 快照。

#### 剩余风险

- 当前虽然保留了 `JsonLoader::LoadFile()` 这条 JSON 输入链路，但主界面还没有“选择 JSON 文件并导入”的显式入口。
- 这意味着“统一 DTO / 统一校验 / 统一运行入口”已经完成，但“面向最终用户的 JSON 文件导入体验”尚未完成。

#### 建议

1. 在 UI 中补一个显式的 JSON 文件选择与加载入口。
2. 继续把“当前场景”抽象成明确的仿真任务对象，支持样例切换和任务持久化。

### 3.2 新 schema 与旧 DTO 命名并存问题已基本收敛

#### 现状

外部输入已经统一为：

- `centerFrequencyGHz`
- `bandwidthMHz`
- `shipOrientationDeg`
- `sensitivityDbm`

当前 `DataModel` 中与主输入链路直接相关的 DTO 字段已改为新 schema 命名，例如：

- `receiverCenterFrequencyGHz`
- `receiverBandwidthMHz`
- `shipOrientationDeg`
- `receiverSensitivityDbm`

#### 剩余风险

- 仍有部分 UI 控件成员名、局部变量名保留历史拼写，这些名称不再属于对外接口，但会增加局部维护成本。
- 如果后续继续扩展环境配置 UI 或结果对象，仍需要持续避免把历史命名重新带回 DTO 或文档层。

#### 建议

1. 保持 `SchemaConstants.h -> DTO -> 文档` 三处同口径。
2. 后续仅在局部重构时清理 UI 内部历史变量名，不再把它们视为接口风险。

### 3.3 UI 校验规则与新 schema 语义冲突问题已完成主收口

#### 现状

当前分层已经收敛为：

- `JsonLoader` 只负责字段存在性、类型、固定值、枚举值和未知字段拦截等基础校验
- UI 页面只负责中文界面输入、DTO 组装和基础格式校验
- `DataModel::validateSnapshot()` 统一负责核心语义校验

#### 剩余风险

- 目前环境参数仍缺少独立 UI 编辑页，因此 UI 路径对 `EnvironmentData` 的覆盖还不完整。
- 未来如果新增设备类型或新结果对象，需要继续遵守“接口层基础校验、DataModel 核心校验”的分层纪律。

#### 建议

1. 新增输入字段时先更新 `SchemaConstants.h` 与 `DataModel`，再扩展 UI。
2. 如需做推荐值提示，应与硬约束校验分离实现。

### 3.4 历史样例仍可能误导使用者(忽略),
**因为目前主项目已经清理,而PE_Validation可忽略**

#### 问题

仓库中仍保留：

- `Tests/Test_A.jsonc`
- `Tests/Test_B.jsonc`

它们属于历史样例，不再是主程序标准输入，但如果文档标注不清，会被误认为与 `Tests/Test.jsonc` 等价。

#### 影响

- 新使用者可能继续按旧字段组织数据。
- 分析问题时会把历史样例误当作主链路接口。
- 后续维护时容易重复引入旧字段兼容讨论。

#### 建议

1. 在文档中明确其为历史参考样例。
2. 如后续不再需要，可转移到单独的 `legacy` 或说明目录。
3. 主程序入口、截图和文档示例统一使用 `Tests/Test.jsonc`。

### 3.5 主程序与验证侧指标链路仍未打通

#### 问题

`PE_validation` 已有实验 3 的指标定义和图表结论，但主程序当前真正稳定输出的仍主要是二维场结果。

#### 影响

- “验证侧已有”与“主程序已实现”容易被误混。
- 报告生成功能缺少结构化指标输入。
- 未来要把 notebook 能力迁回 C++ 时，仍要再次梳理数据边界。

#### 建议

1. 先定义主程序侧 EMC 指标结果对象。
2. 再按对象边界迁移 `SCF`、`S3I`、`T_elev`、`D_desense`。
3. 最后再实现报告生成与 A/B 自动对比。

## 4. 中优先级风险

### 4.1 `EnvironmentData` 的主链路口径已基本一致，但环境编辑能力仍未补齐

当前 `EnvironmentData` 的字段名、单位口径和 `validateEnvironmentConfig()` 的约束已与新 schema 对齐，主链路上的文档歧义已经明显收敛。

剩余问题是：

- `EnvironmentData` 仍保留一组回退默认值，用于空模型或 UI 初始态。
- 主界面尚未提供独立的环境参数编辑入口，因此“JSON 输入”和“UI 录入”两条路径在环境参数覆盖能力上仍不对称。

这不会直接破坏 schema/DTO 一致性，但会限制 UI 路径对完整场景的表达能力。

### 4.2 结果对象仍偏“绘图导向”

当前主程序以 `GridMap` 和图表显示为核心，缺少稳定的结构化结果对象来承接：

- 指标计算
- 报告生成
- 场景对比
- 导出接口

如果不先建立统一结果模型，后续每新增一类输出都会重新拼装数据。

### 4.3 线程与任务边界仍偏原型化

当前仿真入口通过 `std::thread` 驱动 `EMC_Engine`，能工作，但对以下场景的支持仍偏弱：

- 取消任务
- 批量任务
- 多场景排队
- 报告生成串联

这不是当前最紧急的问题，但在功能扩展后会变成瓶颈。

## 5. 建议的推进顺序

1. 先消除绝对路径入口，建立稳定的配置加载方式。
2. 统一 `DataModel` 注释、字段映射说明和 UI 校验口径。
3. 定义主程序侧结构化 EMC 指标结果对象。
4. 把验证侧实验 3 指标迁回主程序。
5. 在结果对象稳定后，再接阵型模板、A/B 对比和报告生成。

## 6. 结论

当前最关键的不是继续堆叠界面能力，而是保持以下三者长期同口径：

1. 新 schema 文档
2. 主程序运行时代码
3. `PE_validation` 中的验证结论

这一步已经完成了第一阶段收敛，但还没有走到“接口彻底稳定”。接下来应优先解决配置入口产品化、环境参数编辑入口和 EMC 指标迁移这三类问题。
