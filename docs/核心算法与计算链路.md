# 核心算法与计算链路

## 1. 文档目的

本文档用于说明主程序的计算内核是如何组织和执行的，重点放在传播求解、结果聚合、派生指标计算和数据流转，不展开 UI 细节。

## 2. 计算主链路

当前主程序的核心计算链路可以概括为：

```text
JSONC / UI
  -> DataModel::DataSnapshot
  -> DataModel::validateSnapshot()
  -> TransferToEngine::convertDataModelToFleet()
  -> EMC_Engine
  -> PEPropagationSolver / PEModel
  -> EMCComputationResult
  -> EMCMetricsCalculator
  -> SimulationTaskResult
```

这条链路的关键设计点是把“输入校验”“传播计算”“派生指标计算”“结果对象组装”拆成独立阶段，避免把所有逻辑塞进单一模块。

## 3. 传播求解

`PEPropagationSolver` 负责单发射机的 1D / 2D PE 求解，是当前传播计算的核心求解单元。

### 3.1 输入

- 发射机配置
- 环境参数
- 目标观察平面高度
- 船只与设备几何信息

### 3.2 输出

- 路径损耗场
- 场强或功率分布
- 与单次发射机关联的二维结果

### 3.3 设计边界

- 只关注单发射机求解
- 不处理任务状态
- 不处理 UI 展示
- 不计算 `SCF / S3I / T_elev / D_desense`

## 4. 总场聚合

`EMC_Engine` 负责多发射机传播结果的调度与聚合，输出 `EMCComputationResult`。

### 4.1 职责

- 持有冻结后的 `Fleet` 和输入快照
- 驱动所有发射机的传播求解
- 聚合总场
- 输出可供后续指标计算使用的中间结果

### 4.2 设计边界

- 不直接计算派生指标
- 不直接消费全局 `DataModel`
- 只处理已冻结输入

## 5. 派生指标计算

`EMCMetricsCalculator` 负责把 `DataSnapshot + EMCComputationResult` 转换为 `DerivedMetrics`。

### 5.1 当前指标

- `SCF`
- `S3I`
- `T_elev`
- `D_desense`

### 5.2 为什么拆分

这样可以把“物理求解”与“业务派生指标”解耦，后续新增指标时，不需要改动传播求解本身。

## 6. 结果对象组装

`simSchedulerCtx` 负责把任务输入、聚合结果和派生指标组装成 `SimulationTaskResult`。

### 6.1 结果对象包含

- `taskId`
- `modelType`
- `status`
- `formationSource`
- `presetFormationId`
- `startedAtUtcMs`
- `finishedAtUtcMs`
- `durationMs`
- `errorMessage`
- `summaryText`
- `inputSnapshot`
- `aggregatedField`
- `emitterResults`
- `derivedMetrics`

### 6.2 设计价值

- 结果对象成为 UI、报告、历史任务的统一消费边界
- 避免各模块自行拼装结果
- 便于后续导出和报告扩展

## 7. 性能与效率

当前项目在效率上的核心优化不在于单一算法“魔改”，而在于结构化分层带来的整体效率提升。

### 7.1 冻结输入快照

- 在仿真启动前冻结 `DataSnapshot`
- 避免运行中再次读取全局状态
- 降低线程竞争和状态漂移风险

### 7.2 分离求解与指标

- 传播求解和指标计算分开执行
- 便于单独优化热点
- 便于后续替换或并行化部分步骤

### 7.3 任务级编排

- `simSchedulerCtx` 统一调度
- 任务状态清晰
- 便于后续扩展批处理、排队和取消

## 8. 后续可扩展点

- 多受害机指标扩展
- 更多派生指标
- 结果缓存与历史任务复用
- 更细粒度的中断点与并行调度
